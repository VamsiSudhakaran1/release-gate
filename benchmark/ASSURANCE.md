# release-gate assurance benchmark — results

> Generated by `python benchmark/assurance.py --md`. The corpus is `release_gate/assurance/corpus.py`; re-run it yourself.

**Corpus:** 16 constructed cases across 16 kinds. **16 of 16 pass.**

## What this measures, and what it does not

Every case here is **constructed**, so its evidence structure is known by construction rather than by judgement. That is the ground truth: whether release-gate correctly reports the structure it was given.

It is **not** a measurement of whether a release is safe. A case labelled `invalid_release` means *a case whose evidence structure carries a named defect that was put there*, never *a release that was actually bad*. Release-gate holds no truth about release safety and claiming one here would be the universal truth claim Invariant 10 refuses.

| This benchmark… | |
|---|---|
| measures release safety | **False** |
| measures the static scanner | **False** — `benchmark/run.py` does, over a different corpus |
| generalises to unseen case shapes | **False** — constructed cases prove the engine handles these constructions |
| is a third-party audit | **False** — same author as the engine, published so it can be re-run |
| establishes that a PROMOTE was correct | **False** — a PROMOTE is a recommendation to a person (Invariant 15) |

## Precision, and where it lives

One precision figure, at the **case** level: of the cases the gate stopped, how many had a defect built in?

| | |
|---|---|
| Cases stopped that had a defect built in | **6** |
| Cases stopped that were clean | **0** |
| Precision | **100.0%** |

There is deliberately **no per-class precision**. A false positive is only ever counted against a clean case, so a detection-class precision would be 1.0 by construction — a number that can only come out perfect, which is worse than no number. And a structural defect legitimately produces a cascade: a failed verification really does create a contradiction and a replication disagreement, so counting the unexpected-but-correct siblings as false positives would be wrong in the other direction. Precision belongs where the clean cases can make it come out wrong.

**Detection is not gating, and the two are separate columns.**

Detected and promoted anyway: `false-independence`, `fake-verifier`, `missing-provenance`. These raise only advisory findings. That is a reportable property of the engine, not a corpus failure — but a table that showed detection alone would let a rule that fires read as a rule that stopped something.

## Per class

| Class | What it asks | Cases | Rules expected | Found | Missed | Stopped | Recall | Behaviours |
|---|---|---|---|---|---|---|---|---|
| DETECTION | a named defect is present — did the right rule fire? | 9 | 13 | 13 | 0 | 6 | 100.0% | 11/11 |
| QUIET | nothing is wrong — did it stay quiet? | 3 | 0 | 0 | 0 | 0 | — | 9/9 |
| BEHAVIOUR | what did it *do*? (no positive class) | 4 | 0 | 0 | 0 | 1 | — | 10/10 |

A `—` means the question does not apply to that class. It is not a 100% that was rounded, and it is deliberately not rendered as one: a QUIET case has no defect to recall, and a BEHAVIOUR case has no positive class at all.

**A false positive on a QUIET case is a *blocking or holding* finding, not any finding.** Advisories are excluded: "nothing declared what this system is permitted to do" is a true statement about a case with no manifest, and counting it against a clean case would make the corpus reward silence. Findings the active methodology *accepted* are excluded too — an acceptance is a decision taken in advance that a structural fact does not disqualify here, and the finding still stands and is still shown.

## What each case builds in

Written from the construction, before the engine was run against it. An expectation written after a run records what the engine does, which is a tautology wearing a test's clothes.

**`valid-release`** — none: subject identified, execution reconstructed, consequence stated, two producers, no contradiction, no mutation
  <br>*Promotes without needing an acceptance — RG-ZC-005 does not fire — so it is a cleaner baseline than a case promoted by waiver.*

**`invalid-release`** — the test-suite verification attempt on the load-bearing claim reports FAILED, while the static-analysis one still reports PASSED
  <br>*RG-VERIF-003 is the pair: a claim with both a passing and a failing attempt is not a claim with one result.*

**`incomplete-evidence`** — CI declares a five-job matrix; two jobs reported

**`false-independence`** — the test run and the static analysis have different producers but both derive from one build fixture, so the second opinion is the first opinion twice
  <br>*Detected and ADVISORY: the case still promotes. Reported as found, not as blocked — see the results table, which keeps detection and decision in separate columns for exactly this reason.*

**`fake-verifier`** — a third attempt claims a FORMAL_PROOF passed while citing no evidence and recording no independence lineage
  <br>*The engine never credits a declared attempt as admissible verification at all (§10r), so the finding is about corroboration: a second opinion that says nothing about where it came from cannot be shown to rest on anything different from the first.*

**`stale-approval`** — a reviewer approves the case; the service is then rebuilt and the same evidence resubmitted against the new digest
  <br>*The approval is taken through the real two-step — offer, acknowledge, submit — because an approval the corpus constructed by hand would not exercise the binding that is the whole point.*

**`artifact-mutation`** — service.py changes digest between the two states while the verifications still name the old one
  <br>*The mutation events are computed by comparing the two cases, not declared by the corpus: a mutation the corpus asserted would test the assertion rather than the engine.*

**`open-contradiction`** — a nightly run contradicts the load-bearing claim and nothing answers it

**`resolved-contradiction`** — none: a counterexample was found, traced to a stale fixture, and resolved with the evidence that settled it
  <br>*The pair to case 10. Same record type, same target, opposite status — so a scorer that confused 'a challenge exists' with 'a challenge stands' would fail one of the two.*

**`unresolved-counterexample`** — a property test found a double-charge sequence and nothing answers it

**`missing-provenance`** — no evidence record names a producer, so every record falls back to the document's own envelope
  <br>*RG-PROV-002 is the sharper of the two: everything tracing to one producer means the corroboration in this case is one party agreeing with itself.*

**`single-agent-action`** — none: a migration with tests, a dry run and a stated consequence
  <br>*Promotes *with* an acceptance (RG-ZC-005), unlike case 1 — the methodology tolerates the single-producer and no-independent-check holds for a bounded, reversible action. The finding still shows.*

**`evidence-omission`** — CI declares a five-job matrix and none of the five reported — total omission, not a shortfall
  <br>*This case failed when it was written. Four of five arriving held the case; none of five arriving PROMOTED it, because the ledger routed total absence to a state no rule read. The pair with case 3 is the regression guard (Invariant 13).*

**`unknown-completeness`** — a trace with no declared step count, so whether it is the whole run cannot be established either way
  <br>*Scored as behaviour, never as detection. 'Correctly said it did not know' has no positive class, and counting it as a hit would let a detection rate rise by declining to answer (Invariant 3).*

**`wrong-target-digest`** — both verifications name an applies_to_digest that no artifact in the case carries
  <br>*RG-ACT-004 fires too, but that is the methodology's requirement rather than a structural finding, so it is not scored here.*

**`ten-thousand-agents`** — none injected: a full-scale research workflow with the phenomena that occur naturally at that size
  <br>*Not a detection case. There is no injected defect to find, and the question is whether a workflow with thousands of contributors still reports what it does not know (Invariant 6).*

## The behaviour checks

Each answers a question precision cannot. They read what the engine returned, never the corpus's own expectations, so a check cannot pass by agreeing with the case that produced it.

|---|---|
| `approval_says_why_it_stopped` | Does it say why, rather than going quiet? |
| `approval_stops_binding` | Does an approval of one state stop binding when the case moves? (Invariant 11) |
| `completeness_not_claimed_complete` | Does the engine refrain from claiming a complete execution? |
| `completeness_unknown` | Is execution completeness reported UNKNOWN rather than guessed? |
| `coverage_reported` | Is coverage reported alongside the verdict? (Invariant 9) |
| `did_not_promote` | Did the engine decline to promote? |
| `mutation_invalidates_its_verifications` | Is a verification of changed content reported as no longer applying? |

| `nothing_blocking` | Did the structural analysis find nothing disqualifying? |

## Known limitations, kept here on purpose

- **No envelope-only case can carry an admissible verification.** `verification_method` on a submitted record is kept as a *declaration* and never credited, because a producer naming its own method is self-certification (§10r). So "valid release" here means structurally sound and self-consistent, never *verified*. Admissible verification reaches a case through a verifier adapter, which is a different input kind.
- **Self-verification by identity alone is not separately flagged.** A claim naming its own producer as verifier raises no rule of its own — the engine never credits a declared attempt as verification in the first place, so there is nothing to withdraw. Reported here as a scope note rather than a detection.
- **Detection and decision are separate columns.** `false_independence` is detected and ADVISORY: the case still promotes. Collapsing the two would let a rule that fires count as a rule that stopped something.
- **Sixteen cases is sixteen cases.** Every rate above is over a denominator small enough to print, which is why the denominators are printed.
