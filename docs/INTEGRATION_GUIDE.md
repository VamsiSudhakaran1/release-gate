# 🔗 Integration Guide

How release-gate fits with the tools already in an AI release pipeline. Every
command on this page runs as written.

---

## The relationship model

release-gate is an admission controller. It does not test, scan, trace or guard
anything itself to reach a decision: it reads what those tools produced, binds
each result to the exact candidate being released, and decides PROMOTE, HOLD or
BLOCK against the declared release policy.

| Tool | The question it answers |
|---|---|
| Linter | Is the code well written? |
| SAST | Does the code contain known vulnerability patterns? |
| Guardrail | Should this live interaction be allowed? |
| Evaluator | How did the agent behave in these tests? |
| Observability | What happened when the system ran? |
| **release-gate** | **Does the evidence establish that this exact candidate satisfies its release policy?** |

```text
 build ─▶ tests ─▶ evals ─▶ scanners ─▶ collect evidence ─▶ release-gate assure ─▶ PROMOTE ─▶ deploy
                                                                │                 HOLD ────▶ a person, then deploy
                                                                │                 BLOCK ───▶ stop
                                                                └─▶ Admission Report (JSON + text)
```

Three things hold for every integration:

- **Results are read, never re-run.** A promptfoo pass rate stays promptfoo's, a
  SARIF severity stays the scanner's own. The Admission Report lists every source
  as *generated by release-gate* or *imported*.
- **No score decides.** release-gate never thresholds an evaluator's score into a
  verdict. A failed check, a succeeded attack or a counterexample bears on the
  claim it is about, and the declared policy says what that does.
- **Evidence binds to a state.** A result about another commit, model or
  environment does not count toward a claim about this one.

## Getting evidence in

`release-gate assure release.jsonl --evidence DIR` reads every `.json`, `.jsonl`
and `.sarif` file in `DIR`. The shape of each is detected from its content:

| You already have | Read as |
|---|---|
| OpenTelemetry (OTLP JSON, GenAI semantic conventions) | an execution trace |
| Langfuse export | an execution trace |
| Arize / Phoenix (OpenInference spans) | an execution trace |
| promptfoo results | an evaluation, each test case its own result |
| SARIF 2.1.0 from any static analyser | static findings, with the analyser's own severities |
| Formal verifier reports (`release-gate.formal/1`) | verification attempts, proof-carrying where the method is |
| An eval harness, a red team, a review, a behavioural evaluation | the generic contracts `release-gate.eval/1`, `red-team/1`, `review/1`, `behavior/1`, and `sast/1` for scanners without SARIF |
| release-gate's own audit report | static findings as Universal Evidence |
| Anything else | `UNRECOGNISED`: still a case, stating that it could map nothing |

The contracts, with one sample each, are in
[`examples/evidence/`](../examples/evidence/README.md). The platform guides in
[`integrations/`](../integrations/README.md) show the export step for Langfuse,
promptfoo, OpenTelemetry and Arize, and a labelled example maps ProofAgent's
evaluation record to `behavior/1`.

A tool with no adapter and no contract can be read through one written in
Python: register an `EvidenceAdapter` on a `ProducerRegistry` and pass it to
`release_gate.assurance.zero_config.assure(path, producers=registry)`. Nothing in
the engine names a producer
([producer contract](REFERENCE.md#evidence-producers--adding-a-source-without-changing-the-engine)).

## In CI

### GitHub Actions

```yaml
- uses: VamsiSudhakaran1/release-gate@v0.11.2
  id: admission
  with:
    command: assure
    input: release.jsonl
    evidence: evidence
    methodology: general-agent-action@1.0.0
    hold-policy: normal          # normal: HOLD goes to a person · strict: HOLD stops
```

The step sets `decision` (PROMOTE, HOLD or BLOCK) and `admission-report` (the
JSON report's path) as outputs. The full pipeline, with a protected review
environment for HOLD, is
[`ci-templates/admission/github-actions.yml`](../ci-templates/admission/github-actions.yml).

### GitLab, Jenkins, CircleCI, Azure Pipelines

[`ci-templates/admission/`](../ci-templates/admission/) has one template each.
Every template runs the same command, reads the Admission Report's own decision,
and applies the declared hold policy. The CLI's exit codes are 0 PROMOTE, 10 HOLD
and 1 BLOCK. A HOLD routes to a person under `normal`, or stops pending approval
under `strict`, and never becomes a BLOCK.

### Deployment systems (Kubernetes, ArgoCD, others)

release-gate is a pipeline step, not a cluster webhook. Gate the deploy job on
the step's decision, and keep the Admission Report as the record of what was
admitted, against which state and policy. The signed evidence pack
(`release-gate evidence-pack`) and the AIBOM lock (`release-gate lock`) are what
a runtime policy layer can check the deployed version against.

## Evidence release-gate produces itself

Its own producers are evidence sources like any other:

```bash
release-gate audit . --evidence-out evidence/static-analysis.json   # code-level agent risk
release-gate lock .                                                  # the pinned AIBOM
release-gate authorship --role implementation --from-ci              # who did the work
```

`release-gate pr --base origin/main` gives one verdict on what a pull request
introduced, for review before merge. It is separate from the release decision.

## Coding agents (MCP)

`pip install 'release-gate[mcp]'` and run `release-gate-mcp` to give a coding agent
read-only access to the agent-code scanner, so it can check its own change before
opening a pull request. The server never executes the code it reads.

## Semantic verification (optional)

Some claims are reading problems. `assure --semantic` asks a model, or a panel of
independent models with `--semantic-panel`, about claims the rules left open.
Readings are recorded and never decide; a disagreement between models goes to a
person. Any OpenAI-compatible endpoint, a local model, or a decision-model
service can be configured
([reference](REFERENCE.md#semantic-verifier--a-model-reads-what-structure-cannot)).

## Practices that keep the decision meaningful

1. **State the candidate.** A `candidate` row with the commit, model and
   environment is what binds evidence to the release, and makes stale evidence
   visible as stale.
2. **Declare the policy.** Pass a methodology, and a resolution policy if the
   defaults are not yours. Without a methodology, the decision holds with
   `METHODOLOGY_REQUIRED`.
3. **Keep the report.** `--admission-out FILE` writes the Admission Report as
   JSON whatever is printed: the candidate, the state hash, the policy digests,
   the decision and every source.
4. **Let HOLD reach a person.** A protected environment, a required reviewer, a
   ticket: a HOLD is a question with a named answer, not a soft BLOCK.
